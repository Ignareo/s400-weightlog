# S400 隐私与威胁模型

> 对象：小米体脂秤 S400（`MJTZC01YM`）+ 本 App（`com.weightlog.app`）。
> 协议细节见 [S400-PROTOCOL.md](S400-PROTOCOL.md)，密钥怎么来见 [S400-BINDING.md](S400-BINDING.md)。
> 本文只讨论 **BLE 侧和本 App 自身**；不涉及任何别的仓库 / 别的 App 的实现。

---

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 别人能读到我家秤的体重吗？ | **仅靠 BLE 不能**。广播用每台独立的 16 字节 bind key 做 AES-CCM，没有 key 只能看到 MAC / 型号 / RSSI / **称重时间** |
| 能读别人家那台 S400 吗？ | **不能**，原因同上；没有"无 key 解密"捷径，MIC 校验会直接失败 |
| 最严重的问题在哪？ | 不在协议，在**密钥保管**：bind key 一旦落到别人手里，历史广播也能被回解 |
| 现在还有哪些洞？ | 广播元数据（称重时刻）、重放、GATT 连接占用、bind key 明文存储、预绑定 APK 等同密钥 |
| 邻居用老款秤会怎样？ | `0x181B` / `0x181D` 那两代**体重明文广播**，蓝牙范围内谁都能读 |

**协议这一层是加密的；真正要小心的永远是"钥匙怎么传"。**

## 1. 广播里能拿到什么

S400 的广播帧（`0xFE95`，MiBeacon v5）里 MAC、product id、counter 是明文，体重 / 阻抗 / 心率在加密 payload 里：

```text
nonce  = MAC + pid/counter + 帧尾 3 字节
plain  = AES-CCM-decrypt(bindKey, nonce, aad=0x11, ct, tagLen=4)
```

| 旁观者能拿到 | 拿不到（无 key） |
|---|---|
| MAC（**固定地址**，不是随机地址） | 体重 |
| 广播名（含 MAC 末 4 位）、型号 `MJTZC01YM` | 阻抗（低频 / 高频） |
| RSSI（可估距离、判断在不在家） | 心率 |
| 心跳包频率（约 0.3–0.6 秒一包） | profile、体脂 |
| **称重发生的时刻与次数**（结果包只在称重末尾出现） | 历史称重记录 |

**即使一个字节都解不开，「什么时候称重」本身就是隐私**——体重包只在有人站上秤时出现，长期记录就能推断作息、在家 / 不在家、家庭成员数量。BLE 广播是**被动接收**，被扫的一方无法察觉，协议层也没有"禁止广播"开关。

### 为什么读不到别人家那台

同样型号、同样加密。要读它需要它的 bind key，来源只有：对方的米家账号、秤被绑在共享家庭、云端泄露 / 账号被接管。BLE 侧没有捷径——AES-CCM 的 MIC 校验会直接失败。

### 例外：老款小米秤是明文

| 服务 UUID | 型号 | 解析 |
|---|---|---|
| `0x181B` | XMTZC02HM / XMTZC05HM / NUN4049CN | `xiaomi-ble` 的 `_parse_scale_v2`（13 字节） |
| `0x181D` | XMTZC01HM / XMTZC04HM | `_parse_scale_v1`（10 字节） |

这两代**体重明文广播、不需要任何 key**，蓝牙范围内都能直接读。第三方廉价秤很多同理。安全性取决于代际和协议，不能一概而论。

## 2. 本 App 的已知暴露面

设计前提是**个人自用**，以下是审查后选择"记录"而不是"修"的限制：

| # | 风险 | 等级 | 现状 |
|---|---|---|---|
| P1 | bind key 以明文存在 App 私有 `SharedPreferences`，没用 Keystore / `EncryptedSharedPreferences` | 中 | `allowBackup=false` 挡得住 `adb backup`，挡不住 root 或能读私有目录的工具 |
| P2 | **预绑定 APK 等同密钥**：`BuildConfig.PRESET_SCALE_BIND_KEY` 是 `classes.dex` 里的明文字符串 | 高（若外发） | 只适合自用 / 自己人安装；对外必须 `--no-preset` 重建 |
| P3 | 设备页「显示」露出 key 时没有 `FLAG_SECURE`，可被截图 / 录屏 | 中 | 自用可接受 |
| P4 | 广播帧无防重放：附近攻击者可原样重放抓到的加密帧，注入一条旧体重，污染曲线 | 中 | 无法伪造新数值（没有 key）；未做去重 |
| P5 | 已绑定 MAC 下，**未加密**的 MiBeacon 体重帧也会被当成本秤数据（1.0 起的老行为） | 中 | 只有"扫描添加 / 自动纠正地址"路径才强制校验加密 + 解密成功 |
| P6 | BLE 元数据：固定 MAC、名字含末 4 位、心跳频繁 → 称重时间线可被完整旁观 | 中 | 无解，只能靠物理距离 / 户型缓解 |
| P7 | GATT 连接不需鉴权即可占用：任何人可占住唯一连接位 → 称重时广播中断、体脂显示 `----` | 低 | 本 App 不建 GATT，因此也受别人占用影响 |
| P8 | bind key / token 来自米家云按账号下发；换账号 / 重置即轮换 | — | 轮换后旧 key 失效，但**已抓到的历史广播仍可被旧 key 解密** |

本 App 侧没有暴露面的部分：**权限里没有 `INTERNET`**，不联网、不上传；key 不打印、不导出、不进日志、不进 CSV / JSON；页面只回 `bindKeySet` / `tokenSet` 布尔值；`allowBackup=false`；`usesCleartextTraffic=false`。

## 3. 怀疑 key 泄露怎么办

怀疑 bind key 外泄（截图、发群、仓库误传、APK 外发、被蹭网）：

1. **米家 App 里解绑并重新绑定秤** → bind key 轮换（只从 App 里删配置不会让旧 key 变安全）；
2. 重新用 token extractor 取新的 `BLE KEY`；
3. 本 App 设备页重填 key（MAC 通常不变），或用新 key 重新构建预绑定包；
4. 清理存过密钥的位置：`.env`、终端 scrollback、聊天记录、截图、旧 APK；
5. 如果外部曾拿到过你的**预绑定 APK**，按第 1 步处理——反编译就能取出 key。

> 轮换之后，**之前被抓到的历史广播仍可被旧 key 解密**——这是已发生的泄露，撤不回来；能做的只是让"以后"安全。

## 4. 数据地图

| 数据 | 位置 | 敏感性 | 现状 |
|---|---|---|---|
| bind key（16 字节） | App 私有 `SharedPreferences`；构建时来自仓库外 env 文件 | 极高：能解这台秤全部广播（含历史回放） | 不明文出现在源码 / 仓库 / 日志 / 导出；但 APK 里可能是明文（P2） |
| 秤 MAC / 广播名 | 空口明文；App 配置里 | 低-中：可追踪在场 | 无法关闭 |
| GATT token（12 字节） | 米家云端 / 第三方工具 | 高：可登录实时通道 | 本 App **不存、不用** |
| 称重记录 / 原始广播 | App 私有 `weightlog.db`（SQLite） | 高：个人健康数据 | 不出本机；卸载即丢 |
| 导出的 CSV / JSON | 公共下载目录 `下载/WeightLog/` | 高：个人健康数据 | 不含 key；分享前自己决定 |
| 截图 / 录屏 | 用户自己 | 中：可能带 key | App 无 `FLAG_SECURE` |

## 5. 边界

不做的事：不尝试获取别人秤的 bind key、不做无 key 的暴力绕过；不把别人家的称重时间 / MAC 用于展示或推断家庭状态。

相关法规（中国大陆）：《个人信息保护法》——体重、健康、行踪属个人信息，处理需合法性基础；《网络安全法》——不得非法侵入他人网络或干扰正常功能；《刑法》253 条之一——非法获取公民个人信息情节严重可入刑。

即使"技术上做得到"，未经授权读取他人设备数据也不可以。
